# Argus v0.14.1 — Wake feedback and Command opening

The v0.14 phone test reported that wake detection seemed to work, but gave no sound or vibration and command handling waited for Argus to be reopened. The old cue was sent only when the foreground command recognizer became ready. A stalled activity launch therefore also meant no acknowledgement. Wake notifications shared the quiet ongoing-listening category, and a focused setup selector could block the web handoff even after the activity opened.

## What changed

- A separate **Hey Argus wake alerts** notification acknowledges each detection, using an alerting category with sound, vibration and banner defaults. The ongoing listening notification stays quiet. These are separate events with separate purposes; existing user notification choices are preserved.
- A short ready beep and **two vibrations** signal that command recording has actually started. Wait for this second cue before speaking the command. Silent mode, Do Not Disturb and system volume settings are respected.
- The selected and connected Android assistant service now requests the existing Argus activity directly. Android's system binding grants that selected service background activity launch eligibility. If the app stays hidden, one system assistant-session request is attempted. An ordinary microphone foreground service does not get that privilege, and Argus does not request overlay/accessibility permissions.
- Native activity focus and WebView readiness are checked separately. A fresh wake is replayed after resume, page loading and focus until claimed or expired; replay cannot create a second capture. A paused, locked or expired wake cannot launch a command.
- Focus left on the background setup controls or an empty command field no longer counts as unfinished content. Dirty commands and other focused forms still block automatic capture.
- Setup now distinguishes **selected and connected** from **selected but not connected**. A **Last wake** line records whether the app was waiting to open or reached microphone readiness. A stalled opening produces a notification-tap fallback instead of silently waiting.

## Short phone check

1. Export a backup before any reinstall needed for this debug APK's signing key. Install v0.14.1 and open **Command**.
2. Pause Hey Argus and tap **Test ready sound / vibration**. Expect a brief beep and two vibrations. Use normal sound mode, audible notification volume and Do Not Disturb off for this comparison. This button only tests the cue; it does not start recording.
3. Open **Wake alert settings** and check that **Hey Argus wake alerts** allows alerts, sound/vibration and pop-up presentation. Android/Samsung may use different labels. The ongoing **Hey Argus listening** category is intentionally quiet.
4. Confirm Argus says it is **selected and connected** as the digital assistant. If selected but disconnected, re-select Argus through **Digital assistant settings**. This changes the default digital assistant.
5. Enable Hey Argus with **Run supported local commands after wake** selected. Switch to another app with the phone unlocked and screen on.
6. Say **Hey Argus**. Expect a wake alert, Argus opening, then the ready beep/two vibrations. After the ready cue, say **Remember to bring my keys**. The memory should save without tapping Run or reopening Argus manually.
7. If opening still fails, tap the wake alert to continue within twenty seconds. Note the exact **Last wake** text and whether setup says **selected and connected**. If Command contains unfinished text, use or clear that text before testing automatic capture.

The initial wake alert acknowledges detection; it does not mean the command microphone is ready. If Android suppresses pop-up alerts or sound, its notification settings remain authoritative. A device-specific launch failure is still possible and must be reported as a failure, not interpreted as a command having run.

## Boundaries and validation

The wake model is unchanged. This patch addresses feedback and handoff, not recognition accuracy. Listening remains screen-on/unlocked. Only supported local commands run automatically; reminders and external actions keep their reviewed draft flows. No new permissions or data schema changes are introduced by this patch.

Regression tests cover native launch eligibility, stale/disabled/locked requests, selected-but-unbound assistant state, WebView/native visibility and protection of unfinished input. Android CI compiles the real implementations and runs the native unit suite. Package inspection checks the version, embedded web code, manifest and pinned wake assets. These checks do not establish successful Samsung activity launch, audible output, haptics or real speech capture; the phone check above remains necessary.
